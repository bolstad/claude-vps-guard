Built to survive the machine it runs on

The problem

A single Claude Code session can grow to several gigabytes over a long day of work. On a workstation with 32 GB, that's noise. On a $5 VPS with one or two, it's the kernel's out-of-memory killer picking a victim more or less at random to free up room — and that victim is just as likely to be sshd or the web server sitting next to Claude as it is to be Claude itself. Lose the wrong one and you haven't just lost a conversation, you've lost the machine.

A second, unrelated problem: a session run over SSH lives and dies with that one terminal. Close the laptop lid, let the Wi-Fi hiccup, or get disconnected mid-response, and by default the process is simply gone — along with whatever it hadn't finished saying.

claude-vps-guard exists to make neither of those things true.

How it works

It's three small, POSIX-ish shell scripts, each doing one job: ccx starts or reattaches to a named tmux session running Claude Code; claude-memwatch is a background watchdog that samples free memory; claude-guard inspects it and lets you see or release whatever it has paused. Together they put two independent layers between a session and the machine it's running on.

Layer 1

The per-session cap

On Linux, ccx starts Claude Code inside its own systemd --user scope with a hard MemoryMax (3 GB by default). A session that runs away gets OOM-killed inside its own cgroup. Nothing outside it even notices.

Swap is disabled for that scope alone. Without that, hitting the cap doesn't fail cleanly — the kernel tries to swap the session's pages out first, which turns a contained memory limit into a host-wide disk I/O problem that can stall every other process on the box while it thrashes. Disabled, the session gets a fast, contained kill instead of a slow, shared one — more on why in docs/platforms.md.

Layer 2

The watchdog

claude-memwatch samples available memory every 10 seconds and, before the system gets anywhere near real OOM, SIGSTOPs the single largest eligible process. Frozen, not killed — claude-guard resume <pid> brings it back once memory recovers.

watchdog · Linux + macOS

Only a whitelist of process names can ever be paused — claude, node, python, a handful of others. sshd, tmux, and the shell itself are never candidates, so a struggling machine can never freeze you out of reaching it.

All of it runs inside tmux, which is what makes the rest possible: detach with Ctrl-b d, and ccx <name> reattaches. A dropped connection becomes a reattach instead of lost work.

Where it earns its keep

The two-gigabyte VPS

The default target: a small box that would happily run one focused Claude Code session all day, right up until it doesn't. FLOOR_MB and CRIT_MB give the watchdog room to react before the kernel has to; PROC_HARD_MB catches a single process ballooning even while the box overall still looks fine.

Several accounts, one box

-a <account> points a session's Claude Code at its own config directory, so more than one Anthropic account stays logged in side by side — a freelancer or small agency running work for several clients without re-authenticating every time they switch. The account only has to be given once; it's remembered in that tmux session's own environment from then on.

The connection that drops

Flaky Wi-Fi, a laptop that sleeps, a VPN that hiccups mid-task — none of it touches a session that lives in tmux. ccx <name> reattaches exactly where the terminal left off, mid-response if that's where it was.

The reboot that takes tmux with it

A kernel update, a host migration, a power blip — the box comes back up and every tmux session is gone, along with any memory of which directory or account each one belonged to. Claude Code's own conversation history survives the reboot regardless. ccx resumable reads it back across every account and shows what's actually there, newest first, and whether it's genuinely waiting or already running somewhere else. ccx -c <session-id> skips the bookkeeping entirely — it finds the right directory and account itself, then either drops you into the pane already running it or rebuilds it from scratch.

Trying it

# clone, install, go
git clone https://github.com/bolstad/claude-vps-guard.git
cd claude-vps-guard
./install.sh
ccx

The installer copies the tools to ~/.local/share/claude-vps-guard, links ccx and claude-guard onto your PATH, and registers the watchdog as a user service — systemd --user on Linux, launchd on macOS.

The two layers aren't symmetric across platforms: Linux gets the full treatment, cgroup cap and watchdog together. macOS has no per-process memory limit to hook into, so the watchdog is the only line of defense there — one layer instead of two, but a real one; it's what catches a runaway session before Activity Monitor would even flag it.
